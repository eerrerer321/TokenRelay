# 攻防清單

給站長自己看：哪些攻擊手法已經擋住（附對應的測試），哪些**還沒擋**。
要不要把這份給朋友看，你自己決定。給了等於公開答案，不給比較好玩。

## 給朋友的遊戲規則（建議）

- 只打這個站本身。**不要**打上游 AI 公司、不要打區塊鏈或錢包。
- 不要灌爆流量（DoS）。站是跑在你家電腦上的，灌爆只會證明家用網路很弱。
- 目標是以下任一項：
  1. **白嫖**：用了沒扣錢，或扣得比實際用量少
  2. **偷額度**：用別人的餘額
  3. **假儲值**：沒真的付錢（或付得比較少）卻加到餘額
  4. **偷看**：看到別人的 key、用量、訂單
  5. **拿到上游 key**
- 找到就回報站長，說明重現步驟。

## 已防護

測試檔：`tests/test_relay.py`（轉發與計費）、`tests/test_accounts.py`（帳號）、`tests/test_deposits.py`（儲值）。
另外，每個測試結束時都會自動檢查三件事：帳本加總等於餘額、沒有任何預扣停在 pending、同時請求數的名額全部歸還。

### 轉發與計費

| # | 攻擊手法 | 怎麼擋的 | 測試 |
|---|---|---|---|
| 1 | 餘額只剩一點點，同時打一堆請求，想趁「檢查餘額」和「扣款」之間的空檔透支 | 預扣用單一條件式 SQL，檢查和扣款不可分割 | `test_concurrent_requests_cannot_overspend` |
| 2 | 串流途中故意斷線，想讓伺服器來不及扣錢 | 結算放在回應物件最外層的 finally，並擋住取消；沒拿到用量就收全額預扣 | `test_stream_client_disconnect_is_still_charged` |
| 3 | 斷線後上游還在繼續生成，花站方的錢 | 斷線時主動關閉上游連線。上游會不會因此停止計費，要看上游是否支援取消（OpenRouter 有些供應商不支援） | `test_disconnect_closes_upstream_stream_that_is_still_producing` |
| 4 | 送 `stream_options.include_usage: false`，讓站方拿不到用量 | 站方強制改成 true；還是拿不到就收全額預扣 | `test_stream_forces_usage_and_charges_actual`、`test_stream_without_usage_charges_full_hold` |
| 5 | 每次只送 1 個 token，費用四捨五入成 0 | 費用一律無條件進位 | `test_cost_rounds_up_so_tiny_requests_are_never_free`、`test_tiny_request_is_charged_at_least_one_micro` |
| 6 | 不填輸出上限、填超大值，或用上游不認得的那個欄位（讓上游改用自己的預設值） | 兩種上限欄位都先拿掉，只送「這個模型的上游認得的欄位」，值壓在模型上限內；預扣用同一個上限 | `test_max_tokens_is_normalized_to_the_models_field` |
| 7 | 用參數讓上游多收錢或換成更貴的模型：`n: 10`、OpenRouter 的 `models` 備援、`service_tier`、`plugins`、`web_search_options`、`prediction`、音訊、上游代執行的工具、`cache_control` | **參數白名單**：最外層、messages、內容區塊、tools 都逐層檢查，白名單外的欄位一律拒絕 | `test_cost_amplifying_or_malformed_params_are_rejected` |
| 8 | 送大圖片：請求裡只有一個網址，上游卻按圖片大小收上萬 token | 每個模型要設定「一張圖最多算幾 token」才接受圖片，預設不接受；預扣按這個數字算 | `test_image_request_holds_model_specific_image_tokens` |
| 9 | 指定不在價目表上的模型名稱 | `config.ini` 裡沒列的模型一律回 404，連上游都不會碰到 | `test_unknown_model_is_rejected_without_charge` |
| 10 | 送超大請求塞爆記憶體（也包括不帶 Content-Length、分段上傳） | 邊讀邊算，超過 1MB 立刻中止 | `test_oversized_body_is_rejected`、`test_oversized_chunked_body_without_content_length_is_rejected` |
| 11 | 送 `NaN`、超深的巢狀 JSON、孤立的 Unicode 代理字元（`\ud800`），讓請求「扣了錢卻送不出去」或讓伺服器 500 | 預扣之前就先檢查並編碼好要送給上游的內容，失敗就回 400，連用量紀錄都不會產生 | `test_unforwardable_json_is_rejected_before_hold` |
| 12 | 故意讓上游回錯誤，從錯誤訊息裡看到上游 key | 401/403 改成通用訊息；400 類的原因會轉給使用者，但先遮掉站方 key 與類似 key 的字串；串流裡的錯誤事件、HTTP 200 的錯誤內容也遮蔽 | `test_upstream_auth_error_is_masked_and_refunded`、`test_upstream_request_error_reason_is_shown_but_sanitized`、`test_upstream_key_in_stream_error_event_is_masked`、`test_upstream_key_in_http_200_error_body_is_masked` |
| 13 | （站方的公平性）請求根本沒送出去，或上游明確拒絕，卻被收錢 | 上游網址格式錯誤 → 讀設定檔時就擋下，伺服器不會啟動；連不上、連線池逾時 → 全額退；上游回錯誤（就算錯誤內容讀到一半壞掉）→ 全額退；送出後才逾時 → 不退 | `test_mistakes_are_reported_with_location[bad-port]`、`test_request_that_never_left_is_refunded`、`test_upstream_error_with_unreadable_body_is_still_refunded`、`test_timeout_after_sending_keeps_the_hold` |
| 14 | key 剛被停用，趁請求還在慢慢上傳時繼續花錢 | 預扣的交易裡鎖住這把 key 再確認一次仍然啟用（PostgreSQL 上用 `FOR SHARE`：停用成功之後，不會再有預扣成功） | `test_key_revoked_before_hold_cannot_spend`（PostgreSQL 上的併發未實測，見 L） |
| 15 | （站方的公平性）結算時資料庫短暫出錯，預扣卡住 | 重試 3 次；結算靠 `status='pending'` 條件保證只生效一次，重試不會重複記帳 | `test_settle_is_retried_without_double_booking` |
| 16 | 站長設定錯誤被利用：模型輸出上限填成負數 → 預扣變負數 → 先送額度 | 設定檔只接受正的輸出上限、非負的圖片 token 與價格，錯了伺服器不會啟動；計費層也直接拒絕負的預扣 | `test_mistakes_are_reported_with_location`、`test_negative_hold_is_refused` |

## 尚未防護（已知弱點）

| # | 弱點 | 影響 | 可能的修法 |
|---|---|---|---|
| A | 登入沒有限制嘗試次數 | 可以暴力猜密碼（密碼至少 10 字元、scrypt 很慢，所以會很慢，但沒有被擋） | 同一個 email 或 IP 失敗 5 次就鎖 15 分鐘 |
| B | 預扣是否真的是上限，取決於站長設定與上游行為：`image_tokens` 夠不夠大、上游是否遵守輸出上限欄位、上游是否有「階梯價格」（例如輸入超過某個長度後單價變 2 倍），以及 OpenRouter 會不會因為 `tools`、`response_format` 改選較貴的供應商 | 實際費用可能超過預扣，照實際扣，餘額可能變負數；站方按固定單價收費，上游可能收得更多（站方虧差價）；拿不到用量時只收得到預扣 | 新增模型時查上游文件的最壞情況，售價填最高階梯；OpenRouter 上游在站方這邊固定供應商；定期比對 `usage_logs` 的 `cost_micro` 和 `hold_micro` |
| C | 限流、訂單鎖都存在記憶體裡 | 用 `--workers 2` 以上啟動就會失效 | 只用單一 worker 跑；之後改用 Redis 或資料庫鎖 |
| D | 結算重試 3 次仍失敗、程序在請求途中當機，或關機時請求被強制取消（可能剛好在預扣提交的瞬間） | 那筆預扣停在 pending，等於收全額預扣（站方不會虧，使用者可能多付）；錯誤訊息仍可能寫「這次不收費」 | 站長查 `usage_logs` 的 pending，用 `credit` 指令補償；之後做「啟動時自動補結算」 |
| E | 完全信任上游回報的 token 數 | 上游灌水就跟著灌 | 用 tokenizer 抽查 |
| F | 完全信任 RPC 節點 | RPC 被冒充可以偽造入帳 | 用兩個不同的 RPC 交叉比對 |
| G | 有人沒開單就付款、或付款非常晚（超過 7 天），而同一個金額剛好發給了新訂單；開單高度來自上一次掃描（最多落後一個掃描間隔），這段區塊裡的同金額轉帳也可能對上 | 這筆錢會入到別人帳上（要剛好同金額含尾數，機率很低，而且付錢的人自己吃虧） | 改用每單獨立的收款地址（方案 C） |
| H | 沒有內容審查 | 朋友拿去產生違規內容，上游封的是**站方**帳號 | 接上游的 moderation API |
| I | 用 HTTP 明文跑 | 不在本機時，key 和密碼會在網路上明文傳輸 | 對外開放前用 Caddy 或 nginx 加 HTTPS |
| J | 全站共用一組邀請碼 | 邀請碼外流，誰都能註冊（不過註冊不送額度） | 改成一人一組、用過即失效的邀請碼 |
| K | 超過確認數之後才發生的鏈重組；沒記區塊雜湊 | 已入帳的錢可能其實不存在（BSC 有快速最終性，機率極低） | 改用 RPC 的 `finalized` 區塊標籤 |
| L | SQLite 會把交易排隊執行，部分併發測試在 SQLite 上無法揭露競態 | PostgreSQL 上的併發行為（預扣、停用 key、建 key、掃鏈進度）只經過靜態審查，沒有實際跑過 | 設定 `TEST_DATABASE_URL`，在 PostgreSQL 上跑一次測試 |
| M | 付款期限用「掃到的時間」判斷，不是用區塊時間 | 寬限期最後幾十秒才付款的人，可能在區塊確認前就被作廢，錢進人工處理；反過來，掃鏈積壓時晚付的款仍可能入到自己的訂單 | 讀區塊時間戳，用鏈上時間比對付款期限 |
| N | HTTP 200 但內容是錯誤（OpenRouter 在串流中途出錯就是這樣） | 照「沒有用量」收全額預扣；錯誤內容只遮站方 key，其他診斷（上游帳號、內部網址）會原樣轉出 | 解析錯誤物件，改成站方自己的錯誤訊息，依上游帳單結算 |
| O | 不付款也能佔用尾數 7 天（作廢的訂單也算） | 一個帳號每小時能開 3 張，幾個帳號一起開，約兩週可以把某個熱門金額（例如 10 美元）的 999 個尾數用光，其他人只能換金額 | 限制每個帳號每天的開單數 |
| P | 沒有資料庫遷移（migration）工具 | 資料表欄位有變動時，舊資料庫不會自動補欄位：啟動正常，請求卻會失敗 | 目前：刪掉資料庫重建（資料會清空）；之後導入 Alembic |
| Q | 上游的真實 API key 明碼存在 `config.ini` | 檔案外流（傳錯檔案、雲端同步、備份、截圖）或這台電腦被入侵，上游 key 就外洩，別人可以直接用你的上游額度 | 檔案不要放進雲端同步資料夾；在上游後台設用量上限；外流就到上游作廢重發 |
