# AI 模型轉發站 — 設計文件

> 定位：私人學習專案，自己和幾個朋友使用，並讓朋友嘗試攻擊找漏洞。不對外營運。

## 1. 整體流程

```
使用者的工具（Cherry Studio、Cline…）
  │  base_url = http://你的站/v1     api_key = sk-站方發的 key
  ▼
┌───────────── 轉發站 (FastAPI) ─────────────┐
│ 1. 驗 API key（只比對雜湊）               │
│ 2. 查設定檔裡的模型（沒列的 → 拒絕）      │
│ 3. 算「最壞情況」費用 → 預扣（hold）      │
│ 4. 轉發給上游 channel                      │
│ 5. 從回應讀實際 token 用量 → 結算多退少補 │
└────────────────────────────────────────────┘
  ▼
上游：OpenAI / DeepSeek / 任何 OpenAI 相容 API（用站方自己的 key）

儲值（方案 B：單一收款地址 + 金額尾數辨識）
  使用者建立訂單「我要儲 10 USDT」→ 系統回「請轉 10.0037 USDT 到 0xABC…，30 分鐘內」
  背景程式定期掃鏈上「轉進 0xABC… 的 USDT/USDC」→ 金額對上訂單 → 入帳
```

## 2. 技術選擇

| 項目 | 選擇 | 理由 |
|---|---|---|
| Web 框架 | FastAPI | 非同步，適合「邊收上游、邊吐給使用者」的串流 |
| 資料庫 | PostgreSQL（測試用 SQLite） | 透過 SQLAlchemy，同一份程式碼兩種都能跑 |
| 鏈 | BSC（幣安智能鏈） | USDT、USDC 都有，手續費低；開發先用測試網 |
| 鏈上讀取 | 直接打 JSON-RPC `eth_getLogs` | 不需要 web3 套件，也**不需要私鑰** |
| 設定 | 單一設定檔 `config.ini`（INI 格式，Python 內建 `configparser` 讀） | 站長要填的東西集中一處；不需要額外套件 |
| 使用者網頁 | 純 HTML + JavaScript（Bootstrap 5.3.3、qrcode-generator 1.4.4，從 CDN 載入並鎖定雜湊），由 FastAPI 直接提供 | 不需要 Node.js 或建置工具；網頁和 API 同一個網址，不用設定跨網域（CORS） |
| 管理功能 | 只限本機開啟的後台網頁（`/admin`）＋ 命令列（CLI） | 後台不用帳密，所以「只有本機進得來」是唯一防線：來源 IP、代理標頭、Host 標頭、CSRF 標頭四道檢查（見攻防清單 43–45） |

**收款錢包的私鑰完全不在伺服器上**：伺服器只知道收款「地址」（公開資訊），錢直接進你自己的錢包
（例如 MetaMask）。就算伺服器被攻破，攻擊者也偷不到錢。

## 3. 金額單位

所有金額都存**整數**，單位是 micro-USD（1 = 0.000001 美元），避免浮點數誤差。

- `users.balance_micro = 10_000_000` 代表 10 美元
- 模型價格存「每 100 萬 token 幾 micro-USD」：$3 / 1M tokens → `3_000_000`
- 費用一律**無條件進位**：避免「每次只用 1 個 token，費用四捨五入成 0」的白嫖手法
- 1 USDT = 1 USDC = 1 美元額度（假設穩定幣不脫鉤）

## 4. 資料表

| 表 | 用途 | 重點欄位 |
|---|---|---|
| `users` | 帳號 | `email`、`password_hash`（scrypt）、`balance_micro` |
| `web_sessions` | 網頁登入 | `token_hash`、`expires_at` |
| `api_keys` | 給工具用的 key | `key_hash`（SHA-256）、`key_prefix`（顯示用前幾碼）、`is_active` |
| `usage_logs` | 每次請求 | `hold_micro`（預扣）、`cost_micro`（實扣）、token 數、`status` |
| `ledger` | 帳本：每一筆餘額變動 | `amount_micro`（正負）、`kind`、`ref` |
| `deposit_orders` | 儲值訂單 | `token`、`pay_amount_micro`（含尾數）、`min_block`（開單時的鏈高）、`status`、`expires_at` |
| `chain_transfers` | 鏈上看到的每筆轉入 | `(tx_hash, log_index)` 唯一、`token_contract`、`decimals`、`amount_raw`、`order_id` |
| `chain_cursors` | 掃鏈進度 | `last_block`（已處理到哪）、`last_head`（最近看到的鏈高） |

**帳本不變式**：任何時候 `SUM(ledger.amount_micro) == users.balance_micro`。測試會檢查這件事。

**上游與模型不在資料庫裡**，寫在 `config.ini` 的 `[upstream:名稱]`、`[model:名稱]` 區段，啟動時讀進記憶體：

- 上游的真實 API key 只存在設定檔裡，資料庫外洩也拿不到。代價是設定檔本身要保護好（見攻防清單 Q）。
- 模型的售價、輸出上限、圖片 token 上限在讀設定檔時就驗證（例如輸出上限必須是正數、上游網址格式必須正確），
  錯了伺服器根本不會啟動，不會等到有人呼叫、預扣已經扣下去才出錯。
- 改價格要重啟。用量紀錄（`usage_logs`）存的是當下實際扣的金額，改價不影響過去的紀錄。

## 5. 計費流程（最容易被打的地方）

### 5.1 預扣（hold）

請求進來時，先算「這個請求最貴可能花多少」，從餘額**原子性**扣掉：

```sql
UPDATE users SET balance_micro = balance_micro - :hold
WHERE id = :uid AND balance_micro >= :hold
```

改到 0 列代表餘額不足 → 回 402。這一句 SQL 同時完成「檢查」與「扣款」，所以同時打 50 個請求也
不會透支（如果寫成先 SELECT 查餘額、再 UPDATE 扣款，中間的空檔就會被併發請求鑽過去）。

- **輸入上限**：「實際要送給上游的內容」的 byte 數 + 64，每張圖片再加該模型設定的 `image_tokens`。
  主流 tokenizer 一個 token 至少 1 byte，所以文字的 byte 數一定 ≥ token 數；圖片在請求裡只佔一個
  網址，上游卻按圖片大小收費，各家算法差很多（同一張圖可以從幾百到上萬 token），所以每個模型要
  自己設定，沒設定（0）就不接受圖片。請求帶 `tools` 時再加 1024：上游會自動加一段看不到的
  工具使用說明並算進輸入（Anthropic 約 300～500 tokens），請求的 byte 數裡沒有它。
- **輸出上限**：使用者填的 `max_tokens` / `max_completion_tokens` 都先拿掉，取較小值並壓在
  `max_output_tokens` 內，再用**這個模型的上游認得的那個欄位**（`max_tokens_field`）送出。
  沒填就補上 `max_output_tokens`。如果照使用者給的欄位原樣轉送，上游不認得時會改用它自己的預設值。
- 這是「估計的上限」，前提是站長設定正確：實際費用超過預扣時仍照實際扣，餘額可能變成負數，
  下一個請求就會被擋（見攻防清單 B）。
- 預扣之前會先把要送給上游的內容編碼好：`NaN` 這類 Python 讀得進來、卻無法轉送的值會直接回 400，
  不會發生「扣了錢卻送不出去」。

### 5.2 結算（settle）

- 上游回應帶 `usage` → 按實際 token 數計費，退回 `hold - cost`
  - 輸入裡「快取命中」的 token 改用模型的 `cached_input_price`（沒設定 = 照輸入價）。命中數讀
    `prompt_tokens_details.cached_tokens`（OpenAI 格式）或 `prompt_cache_hit_tokens`（DeepSeek）；
    數字不是整數、是負數或比輸入總數還大 → 當作 0。設定檔不允許快取價高於輸入價，所以預扣仍是上限
- 拿不到 `usage`（斷線、上游沒給）→ **整筆預扣都不退**（站方不承擔不確定的成本）
- 上游明確回錯誤（4xx/5xx）→ 全額退回（就算錯誤內容讀到一半失敗也一樣）
- 例外：504／524（上游前面的閘道等太久先放棄，後面的模型可能照樣跑完、照樣收費）→ 先收全額預扣，
  狀態標成 `upstream_timeout`；站長對照上游帳單，上游沒收費就用「調整餘額」退回（攻防清單 56、T）
- 請求一定還沒送出（連不上、連線池逾時）→ 全額退回
- 送出後逾時或中途斷線 → 不退（上游可能已經在計費）

結算只會發生一次：`UPDATE usage_logs ... WHERE id = :id AND status = 'pending'`，改到 0 列就代表
已經結算過了。所以結算失敗時可以安全地重試（目前重試 3 次）。

### 5.3 串流斷線

使用者可能在串流途中故意斷線，想讓伺服器「來不及扣錢」。對策：把結算放在回應物件最外層的
`finally`，並用 `anyio.CancelScope(shield=True)` 保護，讓連線被取消時結算也照樣跑完；
同時主動關閉上游連線，上游才不會繼續生成、繼續花站方的錢。

### 5.4 參數白名單

只放行已知「不會讓上游額外收費、或費用已經被輸出上限限住」的欄位（`app/relay.py` 的
`ALLOWED_FIELDS`），其他一律回 400。原因：上游能改變實際費用的參數比想像中多，例如
OpenRouter 的 `models`（備援到更貴的模型）、`plugins`，OpenAI 的 `service_tier`（更貴的服務等級）、
`web_search_options`、`prediction`、音訊輸出；用黑名單一定會漏。

逐層檢查：

| 層級 | 允許的內容 |
|---|---|
| 最外層 | `model`、`messages`、`stream`、`stream_options`、兩種輸出上限、`n`（只能是 1）、`temperature`、`top_p`、`stop`、兩種 penalty、`logit_bias`、`logprobs`、`top_logprobs`、`seed`、`response_format`、`tools`、`tool_choice`、`parallel_tool_calls`、`user`、`reasoning_effort` |
| 每則訊息 | `role`、`content`、`name`、`tool_calls`、`tool_call_id`、`refusal`、`reasoning_content`（DeepSeek 思考模式的工具多輪對話要帶回去；算輸入 token，已含在預扣裡） |
| 內容區塊 | `text`、`refusal`、`image_url` 三種，且不能帶 `cache_control` 之類的附加欄位 |
| tools | 只接受 `type: function`（上游代執行的工具會另外計費） |
| `stream_options` | `include_usage`（串流時強制設為 true，確保拿得到用量）、`include_obfuscation` |

使用者的工具如果送了白名單外的欄位會收到 400，訊息裡會寫出是哪個欄位；確認那個欄位不影響計費之後，
再加進白名單。

## 6. 儲值流程（方案 B）

1. 使用者 `POST /api/deposits {token: "USDT", amount_usd: 10}`
2. 系統從「過去 7 天內沒有任何訂單用過」的尾數（0.0001～0.0999）裡隨機挑一個，組出 `10.0037`；
   同時記下「開單當下看到的鏈高」（`min_block`）
3. 背景程式每 10 秒掃一次：`eth_getLogs` 只查**官方 USDT/USDC 合約**發出的、轉給收款地址的
   `Transfer` 事件，而且只處理已經過 N 個區塊確認的事件
4. 金額完全相等、訂單還在 pending、而且轉帳的區塊 > 開單鏈高 → 同一個資料庫交易內完成：
   標記訂單已付款、加餘額、寫帳本
5. 對不上的轉帳記成 `unmatched`，由站長用 CLI 人工處理
6. 掃鏈**追上最新已確認區塊之後**，才把「過期 + 寬限期」都過了的訂單作廢

防護重點：
- **假幣**：任何人都能發一個叫「USDT」的代幣。只認官方合約地址
- **重複入帳**：`(tx_hash, log_index)` 唯一，同一筆轉帳掃到幾次都只入帳一次
- **鏈重組**：等 N 個區塊確認（區塊被推翻的機率隨確認數下降）
- **舊款對到新單**：開單鏈高那個區塊（含）以前的轉帳不能對上（`min_block`）；同金額 7 天內不重發；
  鏈高只能往前推，不會因為 RPC 節點落後而倒退
- **掃鏈落後**：還在補掃積壓區塊時不作廢訂單，準時付款不會因為「還沒掃到」被誤殺
- **初始化順序**：掃鏈程式至少成功跑過一次才開放建單，避免第一次掃描跳過更早的付款；
  `[chain] start_block` 設在未來時，改從目前已確認的區塊開始掃
- **佔用尾數**：每人最多 3 張未付款訂單

## 7. 成功標準（MVP）

1. 使用者可用邀請碼註冊、登入、建立和停用 API key
2. Cherry Studio 之類的工具填 base_url + key 後，可以列出模型並對話（含串流）
3. 每次請求按實際 token 數扣款，並留下用量紀錄；餘額不足回 402
4. 併發請求無法透支；串流中途斷線也會扣款
5. 儲值訂單在鏈上確認後自動入帳，同一筆轉帳不會重複入帳，假幣不會入帳
6. 帳本不變式在所有測試中都成立
7. 站長在 `config.ini` 設定上游與模型價格，用 CLI 手動補帳、處理對不上的轉帳

## 8. 已知限制（之後的階段再做）

- 使用者網頁是單一頁面（`app/static`，Bootstrap + 純 JavaScript）；站長後台在 `app/admin_static`，只限本機（`app/admin.py`）。後台改模型時直接改寫 config.ini 的那幾行（`app/config_edit.py`），並即時套用新的模型與上游設定；其他設定手動改完仍要重啟
- 一個模型只對應一個上游，沒有失敗自動切換
- 支援 `/v1/chat/completions`、`/v1/models`、`/v1/responses`、`/v1/messages`（Anthropic 格式）、`/v1/embeddings`、`/v1/images/generations`（n=1）、`/v1/audio/speech`（`app/apis.py`）。上游要原生支援同一種格式，站方不做格式轉換；每個端點都是參數白名單、先預扣最壞情況再結算。語音轉文字（`/v1/audio/transcriptions`，上傳音檔、按秒數計費）還沒做
- 資安相關的已知弱點列在 [攻防清單.md](攻防清單.md) 的「尚未防護」
